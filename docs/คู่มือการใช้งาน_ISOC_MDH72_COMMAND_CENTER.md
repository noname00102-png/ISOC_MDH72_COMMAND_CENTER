## 1. วัตถุประสงค์และขอบเขตระบบ

ISOC MDH72 COMMAND CENTER เป็นระบบศูนย์ข้อมูล/แดชบอร์ดสำหรับรวบรวมและแสดงข้อมูลเหตุการณ์ด้านความมั่นคงในจังหวัดมุกดาหาร โดยเชื่อมต่อกับฐานข้อมูล Supabase และรองรับข้อมูลพิกัด ภาพประกอบ ข้อมูลผู้ใช้ การบันทึกการตรวจสอบ ตลอดจนแหล่งข้อมูลสภาพอากาศและน้ำตามที่ติดตั้งไว้

ส่วนประกอบหลักที่ยืนยันได้จาก Repository:
- หน้าเริ่มต้น `index.html` เปิดแอปพลิเคชัน `ISOC6_TREND14_PERIODS_FINAL_QA(1).html`
- ข้อมูลเหตุการณ์หลัก: ตาราง `public.threats`
- ภาพเหตุการณ์: ตาราง `public.threat_images` และอาจมี URL ภาพในคอลัมน์เดิมของ `threats`
- ข้อมูลบัญชี/บทบาท: ตาราง `public.profiles` ร่วมกับ Supabase Auth
- บันทึกตรวจสอบ: `public.audit_logs`
- การตั้งค่าระบบ: `public.system_settings`
- ข้อมูลสภาพอากาศ/น้ำบางส่วน: `weather_forecast_history`, `weather_forecast_weekly`, `weather_forecast_monthly` และ Edge Functions ที่เกี่ยวข้อง
- การอัปเดตข้อมูลสดใช้ Supabase Realtime สำหรับตารางที่ตั้งค่าไว้

**หลักการสำคัญ:** ข้อมูลที่แสดงขึ้นกับข้อมูลจริงและสิทธิ์ที่ฐานข้อมูลอนุญาต ไม่ควรใช้ภาพหน้าจอเก่าแทนข้อมูลปัจจุบัน และไม่ควรเปลี่ยนระดับสถานการณ์โดยคาดเดา

## 2. การเข้าใช้งาน

### 2.1 เปิดระบบ
1. เปิดเว็บเบราว์เซอร์รุ่นปัจจุบัน เช่น Chrome หรือ Edge
2. เข้า URL สำหรับใช้งานที่ผู้ดูแลระบบของหน่วยงานแจ้งให้ทราบ หรือเปิดหน้า GitHub Pages ของโครงการ หากหน่วยงานเผยแพร่ไว้แล้ว
3. รอให้หน้าแดชบอร์ดและข้อมูลโหลดเสร็จ
4. หากระบบกำหนดให้เข้าสู่ระบบ ให้ลงชื่อเข้าใช้ด้วยบัญชีที่ได้รับอนุมัติ
5. ตรวจดูว่าข้อมูล วันที่/เวลา และสถานะการเชื่อมต่อแสดงตามปกติ

> Repository มีไฟล์เริ่มต้นบน GitHub แต่เอกสารที่ตรวจสอบไม่ได้ยืนยัน URL สำหรับผู้ใช้ปลายทางของหน่วยงาน จึงไม่ควรถือว่า URL ของ Repository เป็น URL สำหรับใช้งานจริงโดยอัตโนมัติ

### 2.2 หากเปิดหน้าไม่ได้
- รีเฟรชหน้าเว็บหนึ่งครั้ง และตรวจสอบอินเทอร์เน็ต
- เปิดในหน้าต่างไม่ระบุตัวตนเพื่อแยกปัญหาแคช/ส่วนขยาย
- ลองเบราว์เซอร์อื่นที่หน่วยงานอนุญาต
- หากขึ้นหน้าว่าง ให้บันทึกเวลา URL และภาพหน้าจอ (ปิดบังข้อมูลลับ) ส่งผู้ดูแล
- ห้ามแก้ URL, คีย์, หรือโค้ดใน Developer Tools เพื่อเลี่ยงสิทธิ์

## 3. ภาพรวมข้อมูลและการอ่านสถานการณ์

### 3.1 หลักการอ่านข้อมูล
- **เหตุการณ์ (Threat/Incident):** รายการข้อมูลเหตุการณ์หนึ่งรายการในระบบ
- **พื้นที่:** จังหวัด/อำเภอ/ตำบลหรือพื้นที่ที่ระบุในระเบียน
- **พิกัด:** ใช้ระบุตำแหน่งบนแผนที่เมื่อมีข้อมูลละติจูดและลองจิจูด
- **สถานะรายการ:** ระบุว่ายังดำเนินอยู่หรือปิดแล้วตามค่าที่ระบบจัดเก็บ
- **ระดับสถานการณ์:** ใช้สื่อระดับสถานการณ์ตามฟิลด์ `threat_level`
- **ระดับความเร่งด่วน:** เป็นข้อมูลอีกฟิลด์หนึ่ง (`urgency_level`) และไม่ใช่สิ่งเดียวกับระดับสถานการณ์

### 3.2 ตรวจสอบก่อนนำข้อมูลไปใช้
1. ตรวจวันและเวลาของข้อมูล
2. ตรวจชื่อเหตุการณ์ ประเภท และพื้นที่
3. เปิดรายละเอียดรายการเพื่ออ่านคำอธิบาย
4. ตรวจภาพและพิกัดถ้ามี
5. ดูว่าเป็นรายการที่ยังดำเนินอยู่หรือปิดแล้ว
6. ตรวจระดับสถานการณ์และความเร่งด่วนแยกกัน
7. หากข้อมูลไม่ครบหรือขัดแย้ง ให้ประสานผู้รับผิดชอบข้อมูลก่อนนำไปสรุป

อย่าตีความว่ารายการปิดแล้วหมายถึงเหตุการณ์ไม่เคยเกิดขึ้น และอย่านับรายการซ้ำเป็นเหตุการณ์ใหม่โดยไม่ตรวจสอบรายละเอียด

## 4. การบันทึกและแก้ไขเหตุการณ์

> ขั้นตอนด้านล่างเป็นแนวปฏิบัติทั่วไปสำหรับแบบฟอร์มเหตุการณ์ในระบบ ต้องยืนยันชื่อปุ่มและช่องกรอกกับหน้าจอเวอร์ชันที่ใช้งานจริงก่อนอบรมอย่างเป็นทางการ

### 4.1 ก่อนสร้างรายการ
เตรียมข้อมูลจากแหล่งทางการให้ครบเท่าที่มี:
- ชื่อ/หัวข้อเหตุการณ์ที่สื่อสารได้ชัดเจน
- ประเภทเหตุการณ์
- วันและเวลาที่เกิดเหตุ หรือเวลาที่ได้รับรายงาน (แยกให้ชัด)
- จังหวัด อำเภอ ตำบล และสถานที่
- รายละเอียดข้อเท็จจริงที่ตรวจสอบได้
- ระดับสถานการณ์ที่ผู้มีอำนาจ/แหล่งข้อมูลรับรอง
- ระดับความเร่งด่วน หากแบบฟอร์มกำหนด
- พิกัดที่ตรวจสอบแล้ว
- ภาพประกอบที่มีสิทธิ์ใช้และไม่เปิดเผยข้อมูลที่ไม่จำเป็น

### 4.2 บันทึกรายการ
1. เข้าสู่หน้าจัดการเหตุการณ์ตามเมนูที่ระบบแสดง
2. เลือกเพิ่ม/สร้างรายการ (ถ้ามีปุ่มดังกล่าว)
3. กรอกข้อมูลจากแหล่งที่เชื่อถือได้ ห้ามเติมข้อเท็จจริงที่ไม่มีหลักฐาน
4. ตรวจชื่อ ประเภท พื้นที่ วันเวลา และระดับสถานการณ์อีกครั้ง
5. บันทึกหนึ่งครั้ง แล้วรอข้อความผลการบันทึก
6. หากเกิดข้อผิดพลาด อย่ากดบันทึกซ้ำต่อเนื่อง ให้ตรวจว่ารายการถูกสร้างแล้วหรือไม่ก่อน

ระบบเคยมีการเพิ่มการป้องกันรายการซ้ำ โดยตรวจความใกล้เคียงของหัวข้อ ประเภท พื้นที่ และพิกัดในช่วงเวลาสั้น ๆ อย่างไรก็ตาม ผู้ใช้ยังต้องตรวจสอบก่อนบันทึกเสมอ เพราะการตรวจซ้ำอัตโนมัติไม่อาจแทนการพิจารณาข้อเท็จจริงได้ทั้งหมด

### 4.3 แก้ไขข้อมูล
1. เปิดรายการที่ต้องการแก้ไขและยืนยันว่าเป็นรายการที่ถูกต้อง
2. แก้เฉพาะข้อมูลที่มีหลักฐานรองรับ
3. ห้ามเปลี่ยนระดับสถานการณ์เพียงเพื่อให้ตรงกับระดับความเร่งด่วน
4. บันทึกการเปลี่ยนแปลงและเปิดรายการอีกครั้งเพื่อตรวจผล
5. หากการแก้ไขมีผลต่อรายงานหรือการตัดสินใจ ให้แจ้งผู้เกี่ยวข้องตามสายงาน

### 4.4 ปิดรายการ
ใช้สถานะปิดเมื่อมีการยืนยันตามแนวทางของหน่วยงานแล้วเท่านั้น ตรวจว่าการปิดรายการไม่ได้ลบประวัติเหตุการณ์ และไม่ทำให้ผู้ใช้อ่านเข้าใจผิดว่าเหตุการณ์ไม่เคยเกิดขึ้น

### 4.5 กรณีพบรายการซ้ำ
- เปรียบเทียบชื่อเหตุการณ์ ประเภท พื้นที่ รายละเอียด เวลา และพิกัด
- ตรวจว่ารายการหนึ่งเป็นการติดตามผลของอีกรายการหรือเป็นคนละเหตุการณ์
- อย่าลบรายการเองหากไม่มีสิทธิ์หรือไม่แน่ใจ
- ส่งให้ผู้ดูแล/ผู้รับผิดชอบข้อมูลพิจารณา และบันทึกเหตุผลการแก้ไขตามกระบวนการหน่วยงาน

## 5. ระดับสถานการณ์กับระดับความเร่งด่วน

เอกสารตรวจสอบการผลิตของ Repository ระบุค่ามาตรฐานของ `threat_level` ดังนี้:

| ค่าในระบบ | สีที่กำหนดไว้ | แนวทางอ่าน |
|---|---|---|
| ปกติ | เขียว `#22c55e` | สถานการณ์ปกติตามข้อมูลที่บันทึก |
| เฝ้าระวัง | เหลือง `#eab308` | ต้องติดตามสถานการณ์ |
| แจ้งเตือน | ส้ม `#f97316` | มีเหตุให้แจ้งเตือนตามข้อมูลที่รับรอง |
| วิกฤต | แดง `#ef4444` | สถานการณ์วิกฤตตามการประเมิน/คำสั่งที่เกี่ยวข้อง |

**ข้อควรระวัง**
- `threat_level` คือระดับสถานการณ์หลัก
- `urgency_level` คือระดับความเร่งด่วน ซึ่งแยกจากกัน
- ห้ามอนุมานระดับสถานการณ์จากระดับความเร่งด่วน
- หากระดับสถานการณ์ว่างหรือไม่แน่ชัด ให้สอบถามผู้มีอำนาจกำหนด ห้ามเดาเติมเอง
- สีเป็นตัวช่วยมองเห็น ไม่ควรใช้สีเพียงอย่างเดียวในการตัดสินใจ

## 6. ภาพถ่ายและพิกัดเหตุการณ์

### 6.1 ภาพประกอบ
1. ใช้ภาพที่เกี่ยวข้องกับเหตุการณ์และได้รับอนุญาต
2. ตรวจว่าเป็นภาพของเหตุการณ์/พื้นที่ที่ถูกต้อง
3. ตรวจความชัดเจนและความเสี่ยงต่อข้อมูลส่วนบุคคลหรือข้อมูลปฏิบัติการ
4. หากภาพไม่แสดง ให้ตรวจการเชื่อมต่อและสิทธิ์การเข้าถึงก่อนอัปโหลดซ้ำ
5. อย่าลบไฟล์ภาพจาก Storage โดยพลการ เพราะอาจมีรายการเก่าที่อ้างอิงอยู่

ระบบมีทั้งช่อง/URL ภาพแบบเดิมในข้อมูลเหตุการณ์ และตาราง `threat_images` สำหรับข้อมูลภาพ จึงอาจพบรูปแบบจัดเก็บที่ต่างกันตามรายการและช่วงเวลาที่สร้าง

### 6.2 พิกัด
- ตรวจละติจูดและลองจิจูดกับแหล่งข้อมูลที่เชื่อถือได้
- ตรวจว่าจุดบนแผนที่อยู่ในพื้นที่ที่รายงาน
- หากพิกัดไม่ตรง ให้แก้เมื่อมีหลักฐานยืนยันเท่านั้น
- ห้ามเผยแพร่พิกัดละเอียดของสถานที่อ่อนไหวแก่ผู้ไม่มีสิทธิ์

## 7. รายงานและการพิมพ์

1. เปิดมุมมองรายงาน/หน้าจอที่ต้องการใช้ (ชื่อเมนูขึ้นกับเวอร์ชัน)
2. ตรวจช่วงเวลาและเงื่อนไขการกรอง
3. ตรวจว่ารายการปิดแล้วและรายการที่ยังดำเนินอยู่ถูกตีความอย่างถูกต้อง
4. ตรวจระดับสถานการณ์แยกจากความเร่งด่วน
5. ใช้คำสั่งพิมพ์ของระบบหรือเบราว์เซอร์ตามที่มี
6. ในหน้าต่างพิมพ์ เลือกเครื่องพิมพ์หรือบันทึกเป็น PDF และตรวจแนวกระดาษ/ขอบกระดาษ
7. เปิดไฟล์ผลลัพธ์ตรวจว่าตารางไม่ถูกตัด ข้อมูลครบ และวันเวลาถูกต้อง
8. ก่อนส่งรายงาน ให้ผู้รับผิดชอบตรวจทานตามสายงาน

**ข้อจำกัด:** มีหลักฐานว่าแอปมีความสามารถพิมพ์รายงาน แต่ยังไม่มีหลักฐานว่าทุกรูปแบบรายงาน/เครื่องพิมพ์ได้รับการทดสอบในทุกเบราว์เซอร์

## 8. สภาพอากาศและข้อมูลน้ำ

Repository มีการอ้างถึงข้อมูลสภาพอากาศและข้อมูลน้ำผ่านตารางประวัติ/พยากรณ์และ Edge Functions เช่น `get-mukdahan-weather` และ `get-mekong-mukdahan-water`

วิธีอ่านอย่างปลอดภัย:
1. ตรวจเวลาที่ข้อมูลอัปเดตล่าสุด
2. แยกข้อมูลตรวจวัดจริงออกจากข้อมูลพยากรณ์
3. ตรวจหน่วยวัดและช่วงเวลาที่ครอบคลุม
4. หากข้อมูลไม่ขึ้นหรือเก่า ให้ถือว่ายังยืนยันสถานการณ์ปัจจุบันไม่ได้
5. ใช้แหล่งทางการที่หน่วยงานกำหนดประกอบการตัดสินใจเสมอ

## 9. การใช้งานสำหรับผู้บังคับบัญชา

### 9.1 ตรวจภาพรวม
- ดูจำนวน/รายการเหตุการณ์ตามตัวกรองที่หน้าจอมีให้
- ตรวจเหตุการณ์ที่ยังดำเนินอยู่ก่อน
- อ่านรายละเอียดและพื้นที่ ไม่ตัดสินจากตัวเลขสรุปอย่างเดียว
- ตรวจระดับสถานการณ์และความเร่งด่วนแยกกัน
- ตรวจวันเวลาอัปเดตและความครบถ้วนของข้อมูล

### 9.2 ใช้ข้อมูลประกอบการสั่งการ
- ใช้ข้อมูลในระบบเป็นภาพรวมประกอบข้อมูลจากหน่วยงานเจ้าของเรื่อง
- ระบุข้อเท็จจริง สิ่งที่ยังไม่ยืนยัน และข้อเสนอแนะให้แยกกัน
- หากพบข้อมูลขัดแย้ง ให้สั่งตรวจสอบก่อนเผยแพร่หรืออ้างอิง
- เก็บรายงานที่ส่งต่อในช่องทางที่หน่วยงานอนุญาต

## 10. การจัดการผู้ใช้และสิทธิ์

เอกสารบทบาทที่อยู่ใน Repository กำหนดบทบาทเชิงแนวทางดังนี้:

| บทบาท | ขอบเขตตามข้อกำหนด |
|---|---|
| `admin` | จัดการเหตุการณ์ ผู้ใช้ บทบาท รายงาน และการตั้งค่าระบบ |
| `commander` | ดูข้อมูลปฏิบัติการและรายงาน |
| `officer` | สร้างและปรับปรุงเหตุการณ์ |
| `viewer` | อ่านข้อมูลอย่างเดียว |

### หลักปฏิบัติของผู้ดูแล
1. อนุมัติบัญชีตามกระบวนการหน่วยงาน
2. ให้สิทธิ์เท่าที่จำเป็นต่อหน้าที่
3. ตรวจบทบาทใน `profiles` และการยืนยันตัวตนผ่าน Supabase Auth
4. ทดสอบสิทธิ์ด้วยบัญชีแต่ละบทบาทก่อนใช้งานจริง
5. เมื่อบุคลากรย้ายหน้าที่/พ้นหน้าที่ ให้ทบทวนหรือระงับสิทธิ์ตามนโยบาย
6. ห้ามใช้บัญชีร่วมกันหากนโยบายหน่วยงานกำหนดบัญชีรายบุคคล
7. ห้ามส่งรหัสผ่านหรือคีย์ลับผ่านแชต/เอกสารสาธารณะ

**สำคัญ:** การซ่อนปุ่มในหน้าจอไม่ใช่มาตรการรักษาความปลอดภัยที่เพียงพอ ต้องบังคับสิทธิ์ฝั่งฐานข้อมูลด้วย Row Level Security (RLS) ด้วยเสมอ

## 11. การตรวจสอบข้อมูลและบันทึกการทำงาน

ตาราง `audit_logs` มีไว้สำหรับเก็บข้อมูลตรวจสอบการทำงานตามที่ระบบกำหนด ผู้ดูแลควรใช้ตรวจสอบเมื่อมีข้อผิดพลาดหรือมีการเปลี่ยนแปลงที่ต้องติดตาม

แนวทาง:
- ตรวจเวลา ผู้ใช้ การกระทำ และรายการที่เกี่ยวข้องตามฟิลด์ที่ระบบจัดเก็บ
- อย่าแก้หรือลบบันทึกตรวจสอบเพื่อปกปิดการกระทำ
- หากพบรายการผิดปกติ ให้เก็บเวลาและรายละเอียดเท่าที่จำเป็น แล้วรายงานผู้รับผิดชอบ
- ไม่ควรเปิดเผย log ที่มีข้อมูลส่วนบุคคลหรือรายละเอียดระบบแก่บุคคลที่ไม่เกี่ยวข้อง

## 13. แนวทางรักษาความปลอดภัย

- ใช้บัญชีที่หน่วยงานอนุมัติและล็อกหน้าจอเมื่อออกจากเครื่อง
- ไม่เปิดเผยรหัสผ่าน, access token, publishable key ที่อยู่ในบริบทลับ, service-role key หรือข้อมูลเชื่อมต่อ
- คีย์ service-role ห้ามใส่ใน HTML ฝั่งผู้ใช้โดยเด็ดขาด
- ไม่ปิด RLS เพื่อแก้ปัญหาการอ่าน/เขียนข้อมูล
- หลีกเลี่ยงการส่งออกข้อมูลเหตุการณ์/พิกัด/ภาพไปยังพื้นที่จัดเก็บส่วนตัว
- ตรวจข้อมูลส่วนบุคคลและรายละเอียดปฏิบัติการก่อนพิมพ์หรือส่งต่อ
- ใช้ HTTPS และอุปกรณ์ที่ได้รับอนุญาต
- แจ้งผู้ดูแลทันทีเมื่อสงสัยว่าบัญชีถูกใช้โดยไม่ได้รับอนุญาต

## 14. การสำรอง/กู้คืนและการเปลี่ยนแปลงระบบ

### 14.1 ก่อนเปลี่ยนแปลง
1. ตรวจ Repository และ branch ที่ใช้งานจริง
2. อ่านรายงาน audit ล่าสุดและระบุไฟล์ Source of Truth
3. สำรองข้อมูล/ไฟล์ตามนโยบายของหน่วยงาน
4. ทดสอบในสภาพแวดล้อมที่เหมาะสมก่อนเผยแพร่
5. ทำการเปลี่ยนแปลงเฉพาะส่วนที่จำเป็นและตรวจผลกระทบ
6. ทดสอบการโหลดข้อมูล Supabase, RLS, การอัปเดต Realtime, การบันทึก/แก้ไข, รายงาน และหน้าจอที่เกี่ยวข้อง
7. บันทึก commit และผล QA

### 14.2 ห้ามดำเนินการโดยไม่มีการตรวจสอบ
- ห้ามลบตารางหรือข้อมูลจริงเพื่อทดลอง
- ห้ามใช้ข้อมูลจำลองแทนข้อมูลจริงโดยไม่ระบุชัดเจน
- ห้ามเปลี่ยนระดับสถานการณ์จำนวนมากด้วยสคริปต์โดยไม่มีหลักฐาน/การอนุมัติ
- ห้ามลบไฟล์ภาพใน Storage เพียงเพราะไม่พบ metadata ที่คาดไว้
- ห้ามแก้ไฟล์เริ่มต้นให้ชี้ไปยังไฟล์ HTML อื่นโดยไม่ตรวจความสอดคล้องของเวอร์ชัน
